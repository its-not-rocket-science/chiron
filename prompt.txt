PROMPT F1 — Add a CI pipeline that actually gates merges
--------------------------------------------------------------------------------

Read package.json's scripts, docs/ARCHITECTURE.md's testing strategy
section, and docs/SECURITY.md for which test suites need real
credentials (live Supabase RLS tests, live DeepSeek/OpenAI/Mistral
provider tests) before starting — this matters because a naive
"run npm test in CI" will either fail on secrets that don't exist in a
PR context or, worse, silently skip the tests that matter most
(exactly the RLS and injection-resistance suites this project has
leaned on most heavily) without anyone noticing the skip.

Add .github/workflows/ci.yml (or split into multiple workflow files if
that's cleaner — your call) that runs on every push and pull request
against main:

1. Fast, always-runnable checks with no external credentials needed:
   npm run check, npm run lint, npm test (confirm test currently
   passes with no secrets present — check whether any spec files
   currently assume live credentials are available and would error
   rather than skip; if so, fix those specs to skip cleanly via
   whatever pattern the project already uses, e.g. the existing
   describe.skipIf(!hasApiKey) convention mentioned in earlier prompts
   — don't leave CI red because of tests that were only ever meant to
   run locally with real keys).
2. npm run build, to catch build-breaking changes.
3. A separate job (or a clearly gated step) for the live-credential
   suites — RLS/adversarial database tests and live provider
   integration tests — that runs only when the relevant secrets are
   available as repository/environment secrets. Decide and document
   explicitly: do these run on every PR (using a real but
   non-production Supabase project and API keys with spend limits), or
   only on merges to main, or manually via workflow_dispatch? Cost and
   the risk of a malicious/accidental PR burning API spend both matter
   here — pick a defensible default and record the reasoning in
   docs/DECISIONS.md as a new ADR, don't just wire it up silently.
4. Branch protection intent: this prompt can't itself change GitHub's
   branch protection settings (that's a repo-settings action, not a
   code change), but document in the new ADR exactly which checks
   should be marked required once someone with repo admin access sets
   that up, so the CI file isn't just decorative.

Do not add live-credential jobs that would fail (and block merges) for
any contributor who doesn't have those secrets — a fork or an external
PR should still get useful signal from the fast checks even if the
live suites don't run for it.

Add a status badge to README.md once the workflow exists and has run
at least once successfully.

This one has a hard dependency this prompt cannot resolve on its own:
docs/STATUS.md has carried two open governance items since Prompt 30 —
data retention policy, and which student-data-privacy regulations
apply — as explicitly "not Chiron's to invent." A privacy policy that
states a retention period or a regulatory posture nobody has actually
decided is worse than no page at all, because it creates a written
commitment that might be wrong. Do not guess at either of those two
answers in this prompt.

What this prompt CAN do without waiting on that decision:

1. Add /privacy and /terms routes (plain content pages, following
   whatever pattern the simplest existing static-content page in the
   app uses, or a straightforward SvelteKit page if none exists).
2. Write privacy-policy content that accurately describes what the
   app actually does today, verified against real code rather than
   assumed — what data is collected (account email, lesson text,

   vendors are live in production — check ADR-008 and current provider
   config, not just what's been mentioned in passing), and what's
   already true operationally (e.g. docs/SECURITY.md's statements
   about what is and isn't logged). Everywhere the real answer depends
   on the two open governance items, say so plainly in the page itself
   rather than picking a placeholder number — e.g. "we are finalizing
   our data retention timeline" is honest; inventing "12 months" is
   not.
3. Write terms-of-service content covering the basics that don't
   depend on the open governance items: acceptable use, that Chiron's

   make sure the terms are consistent with it, not contradicting it),
   account responsibilities, and a clear statement that the service is

5. Explicitly flag in your summary, and add a TODO-with-owner in

   you honest, accurate placeholder-free content, not a substitute for

PROMPT F3 — Add password reset / account recovery
--------------------------------------------------------------------------------

Read src/routes/login/+page.server.ts and src/routes/signup (whichever
exists) first to match the existing Supabase auth pattern exactly —
this should look like it was written by the same person as the rest of
auth, not bolted on differently.

Supabase Auth has this built in (resetPasswordForEmail plus an
updateUser call once the user lands back with a valid recovery
session) — use that rather than building custom token/email
infrastructure.

1. Add a "Forgot password?" link on the login page.
2. Add /forgot-password: a simple form (email only) that calls
   supabase.auth.resetPasswordForEmail with a redirect back to a new
   /reset-password route. Show the same success message whether or not
   the email actually has an account — don't let this page become a
   way to enumerate registered emails (check whether Supabase's own
   response already avoids leaking that, and don't undo it by branching
   the UI copy on the result).
3. Add /reset-password: the page a user lands on from the email link,
   which reads Supabase's recovery session and lets them set a new
   password via updateUser. Handle the expired/invalid-link case with
   a clear message and a way back to /forgot-password, not a raw error.
4. Confirm Supabase's email templates/redirect URLs are configured
   correctly for this flow in whatever environment config exists
   (check .env.example and any Supabase config already in the repo) —
   if this requires a Supabase-dashboard-side setting this prompt can't
   make from the codebase alone, say so explicitly rather than silently
   assuming it's already configured.

Add tests: the forgot-password form doesn't reveal whether an email is
registered; the reset-password page correctly rejects an expired/
invalid session rather than crashing; a successful reset actually lets
the user log in with the new password afterward (this last one likely
needs to be a live-Supabase test gated the same way the existing RLS
suite is, since Supabase's actual auth flow can't be meaningfully
mocked).

PROMPT F4 — Org member management: remove, change role, transfer admin
--------------------------------------------------------------------------------

Read src/routes/account/org/+page.server.ts's existing actions
(createOrg, invite, revokeInvite, toggleFeatured) and whatever RLS
policies currently govern the memberships table before starting — this
needs to extend the existing admin-only-action pattern those already
use (check how revokeInvite currently verifies the requester is an
admin and follow the same check, don't reinvent it).

Add three new admin-only actions:

1. removeMember: an admin removes an existing member from the org.
   Decide and handle explicitly: what happens to lessons that member
   marked org-shared or public-template (they should almost certainly
   stay in the org's library — a departing teacher's contributed
   examples shouldn't vanish — confirm this is what actually happens
   given however ownership/visibility is currently modeled, don't
   assume). An admin should not be able to remove themselves via this
   action if they're the org's only admin (see action 3 below for why).
2. changeRole: an admin promotes a member to admin or demotes an admin
   to member. An admin cannot demote themselves if they're the sole
   remaining admin — that would leave the org with no admin at all, a
   state nothing else in this codebase is designed to recover from
   (check whether such a state is even currently preventable by RLS or
   only by application logic, and make sure the check happens
   server-side, not just hidden in the UI).
3. leaveOrg (a member, including an admin, removing themselves): same
   sole-admin guard as above — a sole admin must either promote someone
   else first or delete the org, not leave it adminless.

For all three: require the acting user to actually be an admin of that
specific org (matching the existing pattern, not a generic "is an
admin of any org" check), add live RLS/adversarial tests proving a
non-admin member cannot call any of these three actions on themselves
with elevated effect or on anyone else, and that a sole admin is
blocked from self-demoting or leaving without transferring admin
first. Update the org management UI to surface these three actions
per-member (with the sole-admin case disabled/explained in the UI, not
just failing silently server-side when attempted).

Update docs/DECISIONS.md if any of the sole-admin-guard decisions above
involved a real design choice worth recording (e.g. why "block" rather
than "auto-promote the next member" was chosen).
