PROMPT D1 — Fix the duplicate-copy gap and let existing duplicates be cleaned up
--------------------------------------------------------------------------------

Read src/routes/examples/+page.server.ts's duplicate action,
supabase/migrations/*copy_lesson* (the RPC it calls), and confirm the
diagnosis above by reproducing it: duplicate the same example lesson
twice as a test user and confirm two rows result.

Fix in two parts:

1. Idempotency: before calling (or inside) copy_lesson, check whether
   the current user already owns a copy of this source lesson (you'll
   need a way to trace a copy back to its source — check whether
   copy_lesson already records that lineage anywhere, e.g. a
   copied_from_lesson_id column or similar; add one via a new
   migration if it doesn't exist, since without it there's no reliable
   way to detect "already copied" at all, only "has a lesson with the
   same title," which is a much weaker and more fragile check). If a
   copy already exists, don't silently create another — either return
   the existing copy's id so the UI can link straight to it, or (if
   you decide re-copying should be allowed deliberately) surface that
   explicitly rather than staying silent.
2. UX: update the examples page so, after a successful (or detected
   pre-existing) copy, the button/confirmation area clearly shows
   "You already have a copy of this" with a link to it, rather than
   just re-offering "Duplicate and try your own edit" with no memory
   of the prior action. Load this state on page load too (not just
   after a fresh submission in this session) so it's correct on a
   revisit, not just immediately after copying.

Add tests: duplicating the same example twice produces one lesson row,
not two; the second attempt surfaces the existing copy rather than
erroring or silently no-op'ing.

Separately — this is cleanup, not a fix, do it after the above works —
give the two existing duplicate rows from the live database a way to
be removed. If Prompt D2 (lesson delete) isn't done yet, do a one-off:
confirm via a direct query which of the two rows is safe to remove
(they should be identical copies with no divergent edits — confirm
that before deleting either one) and remove the extra one. Don't do
this until you've confirmed both rows really are exact duplicates and
not two lessons that happen to share a title.

PROMPT D2 — Build the lesson detail view, and make lessons editable and deletable
--------------------------------------------------------------------------------

Read src/routes/lessons/+page.svelte, +page.server.ts, the Lesson/
LessonVersion domain types, and how scoring/re-scoring currently works
end to end (the flow used right after a fresh submission) before
starting — this needs to reuse that pipeline, not reimplement it.

Build /lessons/[id]:

1. Server load: fetch the lesson, its current (and, if the schema
   already supports it, prior) LessonVersion(s) and Score, respecting
   RLS — a user should only be able to load their own lesson (or one
   they have legitimate access to via org-shared/public-template
   visibility, matching whatever rule already governs the library view;
   check that page's load function for the existing pattern rather
   than inventing a new one).
2. View: show the lesson's saved text, subject profile, grade level,
   visibility, and its stored score/skill-coverage/suggestions exactly
   the way a freshly-submitted lesson's results are shown today (reuse
   ScoreDisplay/SkillChecklist/SuggestionList — don't build new
   display components for this).
3. Edit: let the owner revise the lesson text (and subject
   profile/grade level) and resubmit for re-scoring, using the
   existing before/after LessonVersion comparison machinery if it's
   already built (check for it — an earlier prompt in this project's
   history specified a before/after comparison view; confirm whether
   it exists as a component you can drop in here, and if it does,
   reuse it rather than building a second one).
4. Delete: let the owner delete the lesson (and its versions/scores —
   check whether cascade delete is already configured at the DB level
   or needs to be handled explicitly). Require a confirmation step
   (a simple "are you sure" state is fine, doesn't need to be a modal
   library) — this is a destructive, unrecoverable action and the UI
   should treat it that way without being alarmist about it.
5. RLS: confirm (with a live adversarial test, matching this repo's
   established standard for this kind of change) that a user cannot
   load, edit, or delete another user's private lesson via this new
   route or its underlying API calls, and that org-shared/public-
   template visibility rules are respected for read access without
   accidentally granting write access to non-owners.

Update src/routes/lessons/+page.svelte so each lesson title actually
links to its new /lessons/[id] page — right now nothing does.

Add tests: edit flow re-scores and preserves version history; delete
removes the lesson and its dependent rows; a non-owner gets a 403/404
rather than the lesson's content, on both the page load and any
underlying API route.

PROMPT D3 — Restructure navigation: trim the header, move the rest to a footer
--------------------------------------------------------------------------------

Read src/routes/+layout.svelte (the entire current nav lives here — no
separate Nav/Header component exists yet, contrary to what you might
expect from the file naming elsewhere in the project) before starting.

Redesign the navigation structure rather than just visually
compressing the same seven links into less space:

1. Header (top): keep this to what someone needs on every single page
   regardless of what they're doing — the Chiron wordmark/logo linking
   home, and an account affordance (signed in: an avatar/email menu
   containing "My org" and "Log out" tucked inside it rather than as
   separate top-level links; signed out: Log in / Sign up). That's the
   whole header on desktop. On mobile, collapse everything (including
   the primary nav below) behind a single menu control.
2. Primary navigation (Practice, My lessons, Dashboard, Library,
   Examples): move these out of the cramped top bar. Pick whichever of
   these fits the product better and say why in your summary: a
   left-hand sidebar (common for an app with this many top-level
   sections a user moves between constantly), or a secondary nav bar
   directly under the header (closer to what exists today, just
   demoted out of the always-visible top strip and given room to
   breathe). Don't put frequently-used daily navigation (Practice, My
   lessons) in the footer — a footer is for things visited rarely, and
   burying the primary way someone moves around the app down there
   would make the app slower to use, not just less cluttered. Reserve
   an actual footer for things that belong there: nothing currently
   exists that needs one (no about/help/legal links yet) — don't
   invent placeholder footer content just to satisfy "move things to a
   footer" if there's nothing real to put there yet; it's fine for the
   footer to end up small or for this prompt to conclude a footer isn't
   the right container for this specific problem, as long as the
   header itself is genuinely decluttered.
3. Active-page indication: whichever nav pattern you land on, make the
   current page visually distinct in the nav (not just relying on the
   URL) — the current flat link list gives no sense of where you are.
4. Every nav element needs a visible keyboard focus state and correct
   semantics (nav landmark, current-page aria attribute) — carry this
   through the redesign, don't treat it as a follow-up.

Component-ize this: extract the new navigation into its own
component(s) under src/lib/components/ rather than leaving it inline
in +layout.svelte, since it'll need real responsive logic (a mobile
menu has open/closed state) that doesn't belong in the root layout
file.

Add a component test confirming the mobile menu toggles correctly and
that the current page is marked as active in the nav.

PROMPT D4 — Full responsive audit and a real visual design pass
--------------------------------------------------------------------------------

This is the biggest and most subjective prompt here — treat it as a
design exercise with a plan-then-build structure, not just "add some
Tailwind breakpoints."

Part A — plan first, don't start writing CSS yet:

Chiron is a tool teachers (and eventually students) use to get honest,
specific feedback on real work — closer to a considered coaching
instrument than a consumer SaaS dashboard. Come up with a compact
design plan before touching code:
- Color: 4-6 named hex values forming a deliberate palette. The
  current UI is bare Tailwind slate-on-white with no accent color
  anywhere — don't just add "an accent color," choose one that fits an
  education/evidence-and-reasoning tool specifically (this is not a
  generic dashboard and shouldn't end up looking like one; also
  specifically avoid the default AI-generated-design tells: don't reach
  for warm cream + terracotta, near-black + one acid accent, or the
  identical-rounded-card-with-soft-shadow kit unless you've actually
  concluded one of those is right for this brief rather than reaching
  for it by default).
- Type: pick real typefaces with a role each (one for headings/UI
  chrome, one for body/lesson text if they differ) and a defined scale
  — right now everything is default Tailwind font sizing with no
  apparent scale logic.
- Layout: how the three-pillar scores, skill checklist, and
  suggestions should actually be laid out to read as a coherent report
  rather than three stacked generic cards — sketch this in prose/ASCII
  before building.
- State this plan in a short docs/DESIGN.md before writing any
  component code, and briefly check it against the anti-patterns above
  before proceeding — revise anything that reads as a generic default
  rather than a choice made for this specific product.

Part B — responsive audit, every route:

Go through every existing route (/, /lessons, /lessons/[id] from
Prompt D2, /library, /examples, /practice and its case-attempt flow,
/dashboard, /account/org, /login, /signup) at three widths — narrow
mobile (~375px), tablet (~768px), and desktop — and fix what breaks.
Particular attention to: the practice-mode case UI (has the most
complex layout — evidence cards, confidence sliders, the tutor
challenge/response exchange — and per docs/STATUS.md was explicitly
built mobile-first, so audit whether it's held up rather than assuming
it's fine), any data tables or score displays that might overflow
narrow viewports, and forms (lesson input, the structured 4-field mode
from an earlier prompt if it's built) staying usable on mobile.

Part C — apply the design plan:

Rebuild the shared components (ScoreDisplay, SkillChecklist,
SuggestionList, lesson/library cards, buttons, form inputs) against
the Part A plan, consistently — not each restyled slightly differently.
Keep the actual information architecture and functionality unchanged;
this is a visual and responsive pass, not a redesign of what the app
does. Respect existing accessibility work already in place (keyboard
navigation, focus states, reduced-motion — check
docs/PHASE2A_IMPLEMENTATION.md or wherever these requirements were
originally specified) rather than regressing it while restyling.

Part D — self-critique before calling this done:

Take (or describe, if screenshots aren't available in this
environment) a pass at each redesigned page and check it against
Part A's plan and against the generic-AI-design tells specifically —
if anything drifted back toward the default look during
implementation, note it and fix it rather than leaving it. Record
anything genuinely tried-and-rejected in docs/DESIGN.md so a future
pass doesn't re-attempt the same dead end.

Add or update visual/component tests only where they test structure
and behavior (mobile menu state, responsive breakpoint-driven markup
changes) — don't write brittle pixel-snapshot tests against a design
that's likely to keep evolving.
