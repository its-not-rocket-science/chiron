PROMPT G1 — Actually fix the classifier injection gap, not just keep measuring it
--------------------------------------------------------------------------------

Read docs/SECURITY.md Section 9, src/lib/providers/classifierCore.ts,
and docs/qa/LLM_CROSS_CHECK_2026-09-21.md's deterministic
injection-resistance section before starting.

The gap has been measured twice now (2/9, then 0/36 on a larger,
more varied sample) but the underlying weakness the security review
identified — evidenceQuote is checked by normalized substring match
against the student's own text, which can't distinguish a genuine
quote from an attacker's injected payload that happens to literally
contain the matching string — has never actually been patched. The
improved measurement is genuine signal that the current attack
framings don't reliably trigger it, not evidence the mechanism itself
is sound. Fix the mechanism.

Design a stronger check that doesn't just pattern-match the same way
the flawed check already does:

1. At minimum, verify the quoted span's surrounding context is
   consistent with genuine free-text student writing rather than
   looking like embedded structured data (e.g. reject a quote whose
   immediate surrounding text contains JSON-like syntax, code-fence
   markers, or other structural markers a real student answer wouldn't
   contain in that position) — this catches the specific "fake
   embedded JSON result" attack shape Section 9 documented without
   needing full NLP.
2. Consider whether the classifier call itself should receive the
   student's text through a more structurally separated channel (e.g.
   confirm it's already using the same delimited-block pattern
   scoringPrompt.ts established for lesson text, and that the
   evidenceQuote check happens against a version of the input that's
   unambiguously scoped to only the student's actual turn, not
   anything else that might be in context).
3. Explicitly reason through, and document in a code comment, why
   your chosen approach doesn't just move the same false-positive risk
   somewhere else — a stricter check that starts rejecting genuine
   quotes because a student happened to write something with unusual
   punctuation is a real regression, not a fix.

Add the new attack framings from the QA sweep (check
docs/qa/LLM_CROSS_CHECK_2026-09-21.md for the exact three novel
framings beyond the original) as permanent additions to the existing
live adversarial test suite for this provider, not just a one-off
script run — this gap needs to stay caught by normal CI (now that G-
series's CI work, i.e. Prompt F1, exists) going forward, not
re-discovered by another manual sweep.

Update docs/SECURITY.md Section 9 to reflect the actual fix, not just
an improved measurement.

PROMPT G3 — Add error monitoring
--------------------------------------------------------------------------------

No error-tracking dependency exists anywhere in this project currently
— confirmed in package.json. Right now, a class of failure affecting
a subset of users (a provider outage, a schema-validation regression
after a prompt change, an RLS policy accidentally tightened too far)
would only be discovered by a user reporting it, not by anyone at
Chiron noticing first.

1. Pick and add a monitoring provider (Sentry is the most common fit
   for a SvelteKit app and has a maintained SvelteKit integration —
   use it unless there's a concrete reason not to, in which case say
   why and pick an alternative).
2. Wire it into: unhandled errors across server routes, the scoring/
   classifier/tutor provider error paths (the ones that already log
   carefully to console per the existing "never log raw lesson/student
   text" discipline — extend that same discipline to whatever gets
   sent to the monitoring service; this needs the same scrutiny as the
   existing console logging, not less, since a third-party monitoring
   vendor is a new place student/lesson data could leak to if this
   isn't done carefully), and client-side unhandled errors.
3. Explicitly audit what gets sent for PII/sensitive-content leakage
   before this ships — reuse the existing "log only error name/
   message, never raw content" pattern already established in the
   scoring route, and add a live-reviewable test or at minimum a
   documented manual check confirming a scoring failure with real
   lesson text in it doesn't end up verbatim in the monitoring
   dashboard.
4. Add basic alerting for the failure modes that matter most: repeated
   provider errors (a vendor outage), a spike in RLS-denied requests
   (could indicate either an attack or a policy regression — these
   look similar from the outside and both deserve attention), and the
   rate limiter's own "fails open" path actually firing in production
   (per the bug F1 found and fixed — this is exactly the kind of thing
   that should now be observable, not just correctly-coded).

Document what's monitored and how to check it in a new
docs/OPERATIONS.md, since this is the first piece of actual production
operations tooling in the project.

PROMPT G4 — Content moderation for public-template lessons
--------------------------------------------------------------------------------

Read the visibility model (private/org-shared/public-template) and
confirm current behavior: any user can currently mark their own lesson
public-template, making it visible to any Chiron user regardless of
org. There is currently no way for anyone — a Chiron-level
administrator, not an org admin — to remove or hide a public-template
lesson once it's live. Low risk at current user counts, growing risk
as the user base grows, which is the wrong direction for a gap to
scale.

1. Add a Chiron-level (not org-level — a new, separate role/concept;
   don't conflate this with is_org_admin, which is scoped to one org)
   moderator capability: the ability to unpublish a public-template
   lesson (demote it back to private or org-shared, owner's choice
   doesn't matter here — the point is removing it from public
   visibility) with a required reason logged.
2. Design who holds this capability carefully — this is new, elevated,
   cross-org access and needs the same rigor as every other RLS
   decision in this project: a live adversarial test proving an
   ordinary user (including an org admin who isn't also a Chiron-level
   moderator) cannot call this action, and that the moderator
   capability itself can't be self-granted through any exposed path.
   If there's currently no concept of a "Chiron staff" user at all,
   this prompt needs to establish the minimal version of one (e.g. a
   flag on a specific known account, or an allowlist — don't over-
   build a full roles system for what's currently a need for maybe one
   or two people).
3. Add a lightweight report mechanism: let any signed-in user flag a
   public-template lesson as inappropriate, logged for the moderator
   to review — don't auto-unpublish on a report, that creates its own
   abuse vector.
4. Document the moderation process (who has this access today, how a
   report reaches them, what "inappropriate" means for this specific
   product's content — a lesson-plan sharing feature has a narrower
   and different risk surface than general user-generated content, and
   the guidance should reflect that rather than importing a generic
   trust-and-safety policy wholesale) in docs/OPERATIONS.md (from G3,
   or a new doc if G3 hasn't run yet).
