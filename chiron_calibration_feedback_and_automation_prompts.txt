Implement a lightweight automated Phase 2A user-test collection and reporting
workflow. This is evaluation infrastructure, not a new product feature.

Read first:

- docs/USER_TEST.md
- docs/EVALUATION_PLAN.md
- docs/STATUS.md
- docs/SECURITY.md
- src/lib/domain/practiceEvaluation.ts
- src/lib/domain/practiceCalibration.ts
- src/lib/domain/practiceSchemas.ts
- src/lib/domain/practiceCases.ts
- practice routes and server APIs
- migrations covering practice_sessions, practice_attempts and
  disposition_checkins
- all practice RLS tests

GOAL

A tester should be able to enter Chiron through a cohort-specific link, complete
the three canonical cases, complete one short in-app questionnaire, and require
no manual data transcription.

After the test, one local command should produce a self-contained anonymised
TXT/JSON report suitable for direct human review or for feeding to an evaluating
LLM.

Do not build a general analytics dashboard.

1. TEST COHORT

Add an optional nullable user-test cohort identifier to practice sessions.

Support an entry URL approximately:

/practice?test=alpha-2026-08

Do not blindly persist arbitrary query strings.

Use a simple server-side allowlist/configuration mechanism appropriate to the
current architecture.

Normal users without a valid test cohort must behave exactly as before.

Preserve the cohort across all three case sessions for the tester.

Add migration and RLS/adversarial tests.

2. USER-TEST FEEDBACK

After a cohort tester completes all three canonical cases, show one lightweight
feedback form.

Capture:

- cases understandable: 1-5
- tutor made me think more carefully: 1-5
- new evidence felt meaningful: 1-5
- tutor felt repetitive: 1-5
- confidence percentages understandable: 1-5
- update-criterion question understandable:
  yes / mostly / no / not_applicable
- did Chiron seem to steer toward a particular answer rather than better
  reasoning: boolean + optional explanation
- would voluntarily do another case: boolean
- what worked best: short text
- what most needs changing: short text

Do not collect names or new demographic data.

Create a user_test_feedback table with owner-only RLS.
No cross-user feedback browsing UI.

Do not require an external survey service.

3. REPORT SCRIPT

Create:

scripts/export-user-test.ts

and package command:

npm run test:user-report -- --cohort <id>

Use the service-role key locally to retrieve cohort data.
Never expose that key to the browser.

Join the cohort's:

- practice_sessions
- practice_attempts
- disposition_checkins
- user_test_feedback

Build EvaluationDataPoint[] and reuse the existing pure functions in
practiceEvaluation.ts wherever possible.

Also reuse practiceCalibration.ts where mathematically appropriate.

Do not duplicate evaluation logic already in the domain.

4. AUTOMATIC METRICS

Report at least:

- number of testers
- cases started/completed
- completion rate overall and per case
- abandonment stage distribution
- initial judgment distribution
- revised judgment distribution
- initial/final confidence
- mean confidence shift
- count moving > one confidence band
- update-criterion completion
- update-criterion consistency statuses
- reflection completion
- tutor action distribution
- initial reasoning signals
- revised reasoning signals
- signals newly added after challenges
- frequency of uncertainty
- disposition check-ins
- survey response means/counts
- voluntary continuation percentage
- perceived-answer-steering reports

Do NOT call these educational efficacy metrics.
They are product/usability/learning-process observations only.

5. PSEUDONYMISATION

The report must not contain:

- email addresses
- Supabase user IDs
- auth tokens
- service-role keys

Map users deterministically within the export to:

Tester 001
Tester 002
...

The mapping does not need to be persisted.

6. RAW TRANSCRIPT SECTION

The report must include a clearly-delimited per-tester/per-case section
containing:

- initial judgement/confidence
- initial learner reasoning
- update criterion if applicable
- tutor questions/actions in sequence
- revealed evidence references/titles
- revised judgement/confidence
- revised reasoning
- detected reasoning signals
- deterministic scoring events
- reflection

This is necessary so a human or evaluating LLM can audit the aggregate metrics
against the actual interaction.

Do not include hidden evidence that the learner never saw or hidden authored
answer/scoring metadata.

7. OUTPUTS

Generate:

artifacts/user-tests/<cohort>/report.txt
artifacts/user-tests/<cohort>/report.json
artifacts/user-tests/<cohort>/report.md

The TXT report must be self-contained and deliberately LLM-readable.

Include:

- generated timestamp
- git commit SHA
- dirty working tree status
- cohort
- tester count
- executive summary
- deterministic warning flags
- aggregate metrics
- survey summaries
- per-case metrics
- per-tester anonymised paths
- raw transcripts

Gitignore generated reports by default.

8. AUTOMATIC TRIAGE FLAGS

Add descriptive product-test flags such as:

CRITICAL:
- one or more testers report apparent answer steering

HIGH:
- completion <70%
- voluntary continuation <50%
- tutor-made-me-think mean <3/5
- evidence-meaningful mean <3/5

MEDIUM:
- repetition mean >3.5/5
- confidence-understanding mean <3.5/5
- update-criterion understanding below 70%
- fewer than 30% of completed cases show at least one newly detected reasoning
  signal after challenge

These are triage heuristics, NOT claims of efficacy and NOT pass/fail educational
standards. State this prominently in the output.

9. FILTERING

Support:

npm run test:user-report -- --cohort alpha-2026-08
npm run test:user-report -- --cohort alpha-2026-08 --tester 003
npm run test:user-report -- --cohort alpha-2026-08 --case causal-inference-1

Add --dry-run where useful.

10. TESTS

Add deterministic tests for:

- cohort propagation
- invalid cohort ignored/rejected safely
- feedback validation
- owner-only feedback RLS
- report pseudonymisation
- no email/user UUID leakage
- EvaluationDataPoint reduction from DB rows
- aggregate calculations
- warning thresholds
- incomplete sessions
- missing feedback
- one tester attempting fewer than three cases

Run the full existing suite including live RLS tests.

11. DOCUMENTATION

Update docs/USER_TEST.md so the operational workflow becomes:

1. create/enable cohort;
2. share one cohort URL;
3. testers complete three cases + in-app survey;
4. run one report command;
5. inspect report.txt;
6. feed report.txt into Prompt 37 / evaluating LLM.

Keep adult-only guidance until Chiron has actual data-retention and
student-privacy-policy decisions.

Do not run Prompt 37 and do not analyse synthetic data as if it were real user
testing.

Stop after reporting changed files, tests and the exact command I should run to
export the first cohort.
